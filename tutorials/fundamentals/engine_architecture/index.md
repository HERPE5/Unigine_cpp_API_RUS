# Engine Architecture


Существуют разные подходы к построению архитектуры игры: от универсальных решений, где логика игры слита с движком, до набора отдельных модулей, каждый из которых отвечает за одну часть функциональности. UNIGINE находится где-то посередине этой шкалы: он включает всё необходимое для создания игры или другого 3D-приложения, за исключением логики приложения, сетевого взаимодействия и ИИ. UNIGINE включает только типовую игровую логику, общую для приложений всех типов, и это сделано намеренно.


Это может не показаться преимуществом, потому что для создания игры нужно проделать большую работу по программированию и самостоятельно реализовать общую функциональность, широко используемую в играх нужного жанра. Однако отсутствие жанрово-специфичной игровой логики не так уж плохо, поскольку это делает UNIGINE библиотекой общего назначения, легко повторно используемой в разных проектах. Более того, разработчики не привязаны к какому-то определённому жанру и могут экспериментировать с несколькими жанрами одновременно, что крайне сложно при использовании специализированного движка. Например, сложно создать смесь шутера и гоночной игры на основе движка, созданного исключительно для шутеров от первого лица. Кроме того, UNIGINE позволяет подключать внешние модули, которые могут содержать жанрово-специфичную функциональность и также могут быть переиспользованы. Всё это делает UNIGINE довольно гибкой основой для широкого спектра 3D-приложений.


Понимание архитектуры UNIGINE очень важно как для разработчиков, так и для создателей контента. Первые будут знать, что им разрешено делать, чего они могут достичь и чего ожидать от UNIGINE. Вторые поймут, как будет обрабатываться их контент.


> **Примечание:** Более подробное и более ориентированное на программистов описание рабочего процесса UNIGINE можно найти в статье [Execution Sequence](../../../code/fundamentals/execution_sequence/index.md).

Всё начинается, когда пользовательское *приложение* вызывает функции [*C++ API*](../../../api/index.md) UNIGINE. Эти вызовы выполняются с использованием C++/C#. [C++ application](../../../code/cpp/application.md) напрямую вызывает функции API. [C# application](../../../code/csharp/application.md) использует *C# Wrapper* (`UnigineSharp.dll`), который, в свою очередь, использует *C Wrapper* (`UnigineWrapper.dll`, `UnigineWrapper.so`) для взаимодействия с API UNIGINE.


Логика приложения может быть реализована прямо в классах [*AppWorldLogic*](../../../code/fundamentals/execution_sequence/app_logic_system.md#worldlogic), [*AppSystemLogic*](../../../code/fundamentals/execution_sequence/app_logic_system.md#systemlogic) и [*AppEditorLogic*](../../../code/fundamentals/execution_sequence/app_logic_system.md#editorlogic) или через набор *компонентов*, используя [*Component System*](../../../principles/component_system/index.md), включённую в API.


> **Примечание:** [*C# Component System*](../../../principles/component_system/component_system_cs/index.md) является частью C# Wrapper.


Функциональность приложения можно расширить с помощью *плагинов движка*. UNIGINE предоставляет набор [ready-to-use plugins](../../../code/plugins/index.md), однако вы можете реализовать собственный. Вы также можете реализовать пользовательские [*Editor Plugins*](../../../editor2/extensions/index.md), расширяющие функциональность [UNIGINE Editor](../../../editor2/index.md).


Вызовы API передаются в *движок*, который инициализирует необходимые ресурсы: регистрирует расширения, загружает базовые данные, файлы конфигурации, файлы пользовательского интерфейса, директории плагинов. Поскольку все эти ресурсы организованы в специальной директории данных и, более того, могут быть [packed](../../../tools/archiver/index.md), они загружаются с помощью *файловой системы*. Кроме того, файловая система отслеживает порядок байтов (endianness) файлов. Обратите внимание, что если вы добавляете файлы в эту директорию после завершения инициализации, вам нужно перезагрузить компонент файловой системы.


После инициализации движок запускает остальные подсистемы. Приведённая выше схема содержит основные из них:


- *App* управляет [main loop](../../../code/fundamentals/execution_sequence/main_loop.md) и контролирует графический контекст (управляет событиями органов управления, обновляет параметры окна).
- *Render* рендерит сцену. Для выполнения своих задач ему нужны дополнительные ресурсы: текстуры, меши и анимации. Необходимые графические ресурсы передаются в Render из *файловой системы*.
- *World* загружает файлы, необходимые для построения текущей сцены, и определяет набор видимых узлов, которые впоследствии будут отправлены в *Render*. World также сообщает *Sound*, когда и как воспроизводить звуки окружения, источники которых размещены где-то в мире и имеют пространственные свойства. World взаимодействует с *Physics*, которая выполняет физические расчёты (обнаружение столкновений, решение сочленений, плавучесть жидкости и т.д.). Проще говоря, World не рисует объекты, не воспроизводит звуки и не выполняет физические расчёты самостоятельно. Вместо этого он делегирует эти задачи соответствующим подсистемам.
- *Game* передаёт в *World* (по запросу) время в секундах, которое потребовалось для завершения последнего кадра. *World* обновляется согласно полученному значению.
- *Physics* управляет симуляцией физики в *World*.
- *Input (Controls)* обрабатывает ввод от *устройств ввода* и передаёт обратную связь. При необходимости приложение может считывать и как-либо обрабатывать полученный ввод.
- *Materials* и *Properties* управляют материалами и свойствами. Они загружаются из *файловой системы*.
- *Sounds* получает звуки из *файловой системы* и передаёт их в *звуковую карту* для воспроизведения.
- *GUI* отрисовывает пользовательский интерфейс. В UNIGINE объекты GUI могут быть как самостоятельными, так и частью отображаемого виртуального мира. В последнем случае они управляются *World* так же, как и другие узлы. Когда отображается отрендеренное изображение, возможно содержащее GUI, пользователь начинает взаимодействовать с миром. Пользователь может влиять на мир с помощью различных устройств ввода. Ввод от этих устройств отправляется в GUI и в *Controls*. GUI обрабатывает ввод, определяет, на какой элемент был выполнен клик, и выполняет соответствующую callback-функцию. Подсистема *Controls* обрабатывает ввод, не связанный с GUI, например, действия игрока в игре. Обратите внимание, что GUI всегда получает данные ввода раньше *Controls* и, следовательно, имеет более высокий приоритет.
